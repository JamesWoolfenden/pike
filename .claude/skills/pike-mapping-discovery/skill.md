# pike-mapping-discovery

`terraform/google` in this repo is a live GCP sandbox (project `pike-477416`) used to discover, by real experiment, exactly which IAM permission(s) each GCP resource/data-source type requires — never by guessing from documentation or naming convention. The result feeds `src/mapping/google/...`, which is the ground truth `pike scan` reads from. **Never write a permission into a mapping file that hasn't been confirmed by an actual GCP API response in this run.** Guessing defeats the entire purpose of this harness.

**Scope:** this skill is specific to this sandbox project and its two-account setup below. Exercised on both GCP data sources and resources (see Status) — resources are meaningfully different; see the dedicated section below before testing one.

**Finding targets:** `internal/coverage/google.md` (repo root) is the authoritative gap list — it lists every resource/data source with *no* mapping file at all, as `./resource.ps1 <name>` / `./datasource.ps1 <name>` commands. A file with empty `apply`/`plan`/`modify`/`destroy` arrays (found by scanning `src/mapping/`) is **not** necessarily a gap — it may already be a confirmed-zero-permission result, or a stale half-finished scaffold; only `google.md`'s absence-of-a-file list is ground truth for "never addressed." Use `resource.ps1 <name>` (or `-type data`) to scaffold a new target: it creates the blank `.tf` file at the right path/naming convention and copies `template.json` into the right mapping location automatically. It also does a **permission lookup** against `terraform/google/google_permissions.json` (GCP's own documented IAM permissions per service, exported via `export_google_permissions.ps1`) and prints candidate permissions — this is a legitimate way to pick a *smarter first guess* for step 5's loop below, not a shortcut around verification. Every candidate, however sourced, still needs a live GCP response before it goes in a mapping file.

## The two accounts

- **`super-438@pike-477416.iam.gserviceaccount.com`** ("super") — `roles/owner` + `roles/resourcemanager.projectIamAdmin`. Used only for: the GCS backend (`GOOGLE_BACKEND_CREDENTIALS`), and applying changes to the `role/` submodule (which manages the custom role itself and the state bucket).
- **`pike-service@pike-477416.iam.gserviceaccount.com`** ("basic") — bound to exactly one custom role, `terraform_pike`. This is the account under test. The root module's `google`/`google-beta` providers (`provider.tf`) authenticate as this account via `local.gcp_credentials_path`, **not** via `GOOGLE_BACKEND_CREDENTIALS` — that env var only covers the backend bucket. A `tofu plan` in the root module is always exercising `pike-service`'s actual, current permission set.

Check both are live before starting:
```
gcloud iam roles describe terraform_pike --project=pike-477416 --format="value(includedPermissions)"
```
This is ground truth for what `pike-service` can currently do — never assume state from a `.tf` file alone; `tofu plan`/an edited file only describes an *intended* change until `apply` has actually run and you've re-queried.

## Known environment gotchas (check these before concluding something is a permissions problem)

- **Make/shell on Windows:** GNU Make falls back to `cmd.exe` if no `sh.exe` is on `PATH` (breaks the Makefile's `VAR=value cmd` recipe syntax entirely). If `sh.exe` *is* resolved (e.g. via `make SHELL="C:\Program Files\Git\usr\bin\sh.exe" ...`), it then **strips backslashes from unquoted shell variable assignments** — `C:\foo\bar.json` silently becomes `C:foobar.json`. Always set credential path env vars (`PIKE_GOOGLE_BACKEND_CREDENTIALS`, etc.) with forward slashes (`C:/foo/bar.json`) regardless of which shell ends up running the recipe.
- **PATH changes don't apply retroactively.** Adding a directory to `PATH` (even persisted to the Machine/User registry value) has no effect on an already-running shell; it only affects new processes. Don't re-diagnose the same issue in a session that predates the PATH edit — open a fresh terminal, or keep using the explicit `SHELL=` override.
- **Two independent, mismatched hardcoded credential paths.** Both `provider.tf` (root) and `role/provider.gcp.tf` hardcode a `local.gcp_credentials_path` with a macOS path checked first, falling back to a Windows path — and the two files currently expect different local filenames than the `pike-gcp-*.json` naming actually used (e.g. `pike-basic.json` / `pike-super.json`, no `gcp-` infix). Match your local files to what the code expects (rename/copy locally); don't "fix" the hardcoded repo paths as a side effect of an unrelated task.
- **PowerShell argument splitting.** Any `tofu`/`gcloud` flag of the form `-flag=value.with.dots` (e.g. `-target=data.x.y`, `-chdir=./role`) must be passed as one quoted string in PowerShell or it gets mis-split into multiple arguments.
- **Git Bash / MSYS path translation.** A leading-slash path (e.g. `-outfile "/foo.tf"`) passed to a Windows exe from Git Bash gets silently rewritten to `C:/Program Files/Git/foo.tf`. Always use a full Windows path or an explicit `./relative` path for tool output files.
- **Service-account key material is only ever returned once**, at `gcloud iam service-accounts keys create` time — it cannot be re-downloaded later. If a key file looks wrong (check which identity it actually authenticates as via `gcloud auth activate-service-account --key-file=... --quiet`, which prints the account), the fix is minting a fresh key, not hunting for the old one.
- **Creating a service-account key is an auto-mode-blocked action.** Expect to hand the exact command to the user to run themselves. Applying the `role/` submodule via raw `tofu "-chdir=./role" apply -auto-approve` was also blocked once, but **`make role` (the Makefile target that runs that same command) was not blocked on any subsequent attempt** — always use `make role` to apply the custom-role change, not the raw `tofu` invocation.
- **PowerShell tool calls do not persist shell state between calls** — only the working directory carries over; environment variables set with `$env:X = ...` in one call are gone in the next. If a persistent `PIKE_GOOGLE_BACKEND_CREDENTIALS` (or similar) exists outside this session with the wrong (backslash) form, a fresh call that doesn't re-set it will silently pick that up and fail with the credentials-parsing error again. Always set the env var in the **same** call as the `make`/`tofu` command that needs it, every time — don't assume a value set earlier in the conversation still holds.
- **IAM custom-role permission changes can take a couple of minutes to propagate** — sometimes longer, up to several minutes, when stacked right after also just enabling the API itself (seen with `redis.aclPolicies.get`: ~2 minutes wasn't enough, ~3+ minutes was) — even after `gcloud iam roles describe` already shows the new permission live. A re-plan immediately after `apply` can still return the *exact same* denial for the permission you just granted — don't treat that as evidence the permission is wrong. Poll (a backgrounded retry loop checking every ~10s) before concluding a candidate is insufficient; start with a ~2 minute cap, and if it gives up, re-confirm the role is actually live (`gcloud iam roles describe`) and run a second, longer poll rather than assuming the permission guess was wrong.
- **`pike.exe` embeds the mapping JSON database at build time (`go:embed`).** Editing/moving a file under `src/mapping/` has no effect on an already-built binary — `pike scan` will silently report "no IAM permissions found" (looking like the mapping is empty or wrong) rather than erroring. Always `go build -o pike.exe` (from the repo root) immediately before the round-trip verification in step 8, every time, even if you built it earlier in the same session.

## Technique: finding the right response in concurrent `TF_LOG=DEBUG` output

When other data sources are still present (restored between isolations, or deliberately left in place because they're inert at the placeholder baseline), `tofu plan` reads them all concurrently, and their request/response log blocks interleave — `grep -A N` after a request line often lands you in a *different* resource's response. Don't guess which response belongs to your target from proximity alone. Instead, find the one `Host:` line unique to your target's API, then correlate by line number against every `HTTP/2.0` response code in the file, in order:
```
grep -n "Host: <api>.googleapis.com" debug.log   # find your request's line number
grep -n "HTTP/2.0" debug.log                      # list all response codes in order
```
With only one request to that `Host`, the first response *after* its line number is reliably its response, regardless of how many other resources' blocks are interleaved around it (used to disambiguate `biglake_hive_catalog_iam_policy` and to confirm `iap_agent_registry_endpoint_iam_policy`'s baseline `404` versus the sibling `agent` subtype's `403`). Redirect to a file rather than piping through `grep` directly when you need to search it more than once (`tofu plan > debug.log 2>&1` with `TF_LOG=DEBUG` set) — delete the file when done, it's scratch output, not something to leave in the repo.

## Process, per resource/data-source type

1. **Find the scaffold.** A new type shows up as a blank `data "google_x" "pike" {}` (or `resource`) file at the `terraform/google` root, paired with an empty-arrays mapping file at `src/mapping/google/data/google_x.json` (fields: `apply`, `attributes.tags`, `destroy`, `modify`, `plan`).

2. **Get the schema, not a guess.** Dump the provider schema once per session (`tofu providers schema -json > <scratchpad>/schema.json`) and `jq` out the target type's `required`-attribute list plus each attribute's `description` (format/character restrictions are often documented there, e.g. ACL-policy-id naming rules). Fill in the blank block with **syntactically valid placeholder values only** — lowercase/hyphen rules etc. satisfied, but the value need not reference a real object. For a `get`/read-style data source, GCP's IAM check fires independently of whether the object actually exists, so a placeholder ID is sufficient to trigger a real, informative API response.

   **For a `resource` type specifically, check for cost-risk signals in this same schema dump, before ever running `apply`.** `jq` the full attribute and block-type name list (not just the `required` ones) and scan for words like `dedicated_infrastructure`, `autoscaling`, `replica_count`, `cluster`, `node_count`, `instance`, `machine_type` — these indicate the resource provisions real billed infrastructure (a GKE cluster, autoscaled serving replicas, VMs), not a lightweight config record. This was learned the hard way, twice in one session: `google_vertex_ai_semantic_governance_policy_engine` (a GKE cluster + tenant project, only noticed via an unusually long `apply` time) and `google_vector_search_index` (`dedicated_infrastructure { autoscaling_spec { min_replica_count = 2 } }`, visible right in the schema dump beforehand but not checked until after creating it — its teardown then ran past 30 minutes). If a cost-risk signal is present, either skip the type outright (the same treatment already given to `google_vertex_ai_persistent_resource`) or flag it to the user and ask before proceeding — don't create it first and plan to destroy quickly.

3. **Isolate the one type under test.** Move every other unfilled `data.google_*.tf`/`resource.google_*.tf` file out of the directory to a holding folder (`$env:TEMP\claude\...-holding` or similar) — OpenTofu validates the *entire* configuration before planning, so any other blank required-argument block blocks even a `-target`ed plan. Leave only the target file.

4. **Pre-enable the likely API, then plan and read the real error.** Before ever running `tofu plan`, derive the probable API service name from the resource type's prefix (e.g. `google_redis_*` → `redis.googleapis.com`, `google_data_catalog_*` → `datacatalog.googleapis.com`, `google_eventarc_*` → `eventarc.googleapis.com`, `google_network_services_*` → `networkservices.googleapis.com`, `google_gemini_data_analytics_*` → `geminidataanalytics.googleapis.com`, `google_oracle_database_*` → `oracledatabase.googleapis.com`) and check it:
   ```
   gcloud services list --project=pike-477416 --filter="config.name:<guess>" --format="value(state)"
   ```
   If it isn't `ENABLED`, enable it now as `super` before planning:
   ```
   gcloud services enable <guess> --project=pike-477416 --account=super-438@pike-477416.iam.gserviceaccount.com
   ```
   This is a time-saving shortcut, not a guess you rely on being right — 5 of the first 18 types hit `SERVICE_DISABLED` reactively, each costing a full plan→enable→replan round trip this skips. If the derived name is wrong or doesn't exist, the reactive handling below still catches a genuine `SERVICE_DISABLED` response.

   Then plan:
   ```
   $env:GOOGLE_BACKEND_CREDENTIALS = "<forward-slash path to super key>"
   tofu plan
   ```
   Outcomes:
   - `403` naming the exact permission (e.g. `does not have storage.objects.list access`) — note it as the first confirmed permission and go to step 5 to check whether a second one is also needed.
   - `403: The caller does not have permission` (no permission named) — go to step 5.
   - `404`/"not found" with no permission error — `pike-service`'s *current* permission set is already sufficient; if you were testing from the full baseline role you still don't know the *minimal* set, so narrow via step 5 using a single candidate.
   - `403` naming a disabled API (`SERVICE_DISABLED` / "has not been used in project ... before or it is disabled") — this is **not** an IAM permission gap, it's the GCP API itself not being enabled on the project yet. Enable it as `super` (`gcloud services enable <api>.googleapis.com --project=pike-477416`), confirm, then re-plan — only *then* does the real permission-related response (one of the other three outcomes) appear.
   - **A GCP API `404` that doesn't change whether a plausible permission candidate is granted or not** — this is a distinct, genuinely-stuck case, not the zero-permission case below. Some GCP APIs (seen with `google_biglake_hive_catalog_iam_policy`'s `getIamPolicy` call to `biglake.googleapis.com`) return `404 Not Found` for a nonexistent object *regardless of the caller's permission* (apparently to avoid leaking resource existence to unauthorized callers, or simply incomplete handling in a newer API) — and some Terraform provider implementations additionally swallow that 404 silently, returning an all-`null` data source result with no visible `plan` error at all, rather than surfacing it. Confirm this is really what's happening (not a propagation delay) by granting an actual plausible candidate permission, re-running, and checking whether the raw HTTP response code changes — use `TF_LOG=DEBUG` and grep for the request/response block if the plain `plan` output shows nothing informative. If the response is identically `404` both with zero relevant permission and with a real candidate granted, the placeholder-ID method cannot determine the permission for this type at all. Don't guess a plausible-looking permission into the mapping file here — stop, restore the role to the placeholder baseline, leave the `.tf` file unarchived (still at the root, not moved to `backup/`), and report the type as blocked pending either a real backing object or another way to test it (see Discipline).
   - **A clean read, or any non-permission error (plain content/not-found error unrelated to auth), while the role is still at the empty-equivalent placeholder baseline (step 9)** — this means the type genuinely needs **zero** IAM permissions. This is a real, *confirmed* finding — just as valid and worth recording as any other result, not a "nothing happened" case to shortcut past. Some data sources call a public endpoint rather than an authenticated GCP API (e.g. `google_iam_workload_identity_pool_jwks`/`_openid_config` fetch a public OIDC discovery/JWKS document over plain HTTPS — there's no IAM check in the path at all). Write an empty `plan: []` array (don't invent a permission just because the field exists in the mapping schema) and still run the *full* remaining process on it — steps 6–8 all still apply, including the archive and the round-trip verify. The one thing to get right at step 8: `pike scan` reporting "no IAM permissions found" is the *correct, confirming* result here — distinguish this deliberately-confirmed empty case from the stale-embed false negative (gotcha above) by the fact that you've *just* rebuilt `pike.exe` for this check, not by assuming either way.

5. **Narrow by single-permission substitution, then loop if needed.** Most types need exactly one permission, but don't assume that going in — some data sources legitimately need more than one (e.g. a `get` plus a separate `list`/sub-resource permission), and GCP often reveals these one at a time rather than all at once. This step is a loop, not a single substitution:

   a. Edit `role/google_project_iam_custom_role.tf`'s `permissions` list down to exactly one candidate to start (standard GCP convention: `<service>.<resource-plural>.<verb>`, cross-check against a sibling already-populated mapping file in the same service subfolder if one exists — e.g. `google_cloudbuild_trigger.json` → `cloudbuild.builds.get` informed the guess for `cloudbuild.workerpools.get`).
   b. Apply, **as `super`**, from the `role/` submodule, via `make role` (see gotcha above on why, not raw `tofu apply`). The full output includes a large, irrelevant `state_bucket` dump every single time — filter it down to just the permissions diff and the completion/error line:
      ```
      make SHELL="C:\Program Files\Git\usr\bin\sh.exe" role | Select-String -Pattern "permissions|Apply complete|Error"   # PowerShell
      make SHELL="C:\Program Files\Git\usr\bin\sh.exe" role 2>&1 | grep -E "permissions|Apply complete|Error"             # Bash
      ```
      Confirm it actually landed — `gcloud iam roles describe terraform_pike ...` must show the new permission list before proceeding; don't trust the apply output alone (auto-mode may have blocked it, in which case hand the exact command to the user and wait).
   c. Re-isolate the target file (other files may have been restored in between) and run `tofu plan` again.
   d. Read the result: if the `403` clears (replaced by a clean read or a plain `404 not found` for the placeholder object), the current list is sufficient — stop and go to step 6. If still denied and this new error now *names* a different, specific permission, **add it to the list cumulatively** (don't replace what's already there) and repeat from (b). If still denied with the same generic "caller does not have permission" message, pick the next candidate, add it cumulatively, and repeat from (b).
   e. Cap at a handful of iterations. If still denied after several plausible candidates, say so explicitly rather than continuing to guess — report which permissions were tried and that the exact requirement couldn't be determined this way (may indicate the type needs a real backing object, not just a placeholder ID — see Discipline).

   The mapping file's final permission array should end up containing every permission accumulated in this loop, not just the last one tried.

   **Minimality check, once sufficient.** If the accumulated list has more than one permission, don't assume all of them are actually required just because the combination worked — re-test with one removed at a time (same apply/re-plan cycle) when there's a plausible reason one might be redundant. This matters most for a lookup-by-attribute data source (filters by name/display_name rather than taking a direct resource ID): these are often implemented as a `list` call filtered client-side, so an initially-plausible `.get` candidate can turn out to be unnecessary once `.list` alone is confirmed to work (seen with `google_data_catalog_taxonomy`: `.get` + `.list` both worked, but `.list` alone was then confirmed sufficient on its own). Only write the genuinely minimal set to the mapping file.

6. **Write the mapping.** Put the confirmed permission(s) into the correct array of `src/mapping/google/data/google_x.json` — `plan` for a data source's read (matches the convention in existing populated files). If a subfolder already exists for that GCP API service (`src/mapping/google/data/<service>/`), move the file into it; only create a new subfolder if the service clearly warrants one and no flat convention is already established for it. For a confirmed zero-permission type (previous step), there's no permission string to derive a service subfolder from — leave the mapping file at the flat `src/mapping/google/data/google_x.json` location rather than guessing a subfolder from the resource name alone.

   **Also add `"verified_date": "<today, YYYY-MM-DD>"` and `"verified_provider_version": "<the hashicorp/google version this session used>"` as top-level keys alongside `apply`/`plan`/etc.** A confirmed-today permission isn't a permanent guarantee — GCP genuinely changes required IAM permissions for an API over time (new requirements added, deprecations, GA promotions), and there is currently **no other mechanism in pike that records when an entry was last empirically checked**. Confirmed safe to add (not assumed): `src/plan.go`'s `getPlanPermissionMap` unmarshals each mapping file into `var mappings []any` — a generic untyped map, not a fixed struct — and looks up only specific known keys by name, so extra fields are silently ignored; verified via a round-trip `pike scan` showing identical output before/after adding these fields, and the full `go test ./...` suite (including `internal/coverage`, which generates the gap-list report) passing unchanged. This is metadata for future staleness-detection, not something pike's current code reads or acts on.

7. **Archive the scaffold.** Move the now-filled `.tf` file from the `terraform/google` root into `terraform/google/backup/` — OpenTofu doesn't recurse into subdirectories, so this parks it as inert without deleting history. Restore any other files you moved aside in step 3.

8. **Round-trip-verify with `pike` itself.** Build if needed (`go build -o pike.exe` from the repo root). Copy **only** the single archived `.tf` file into an isolated scratch directory (never point `pike scan` at the whole `backup/` folder for a single-type check — it holds many unrelated parked resources and the output becomes unreadable noise). Run:
   ```
   GCP_PROJECT=pike-477416 ./pike.exe scan -w -i -e -d <isolated-dir> -outfile <isolated-dir>/role.tf
   ```
   Read the generated `role.tf` and confirm its `permissions` list matches exactly what was confirmed live in step 5. A mismatch means the mapping file (step 6) was written wrong, not that pike is wrong — pike only reflects the mapping database back.

9. **Reset to the placeholder baseline before the next type — always, no exception.** This is mechanical, not a judgment call: the moment a type is confirmed (steps 6–8 done, or blocked per Discipline), immediately set `role/google_project_iam_custom_role.tf`'s `permissions` back to `["logging.logEntries.list"]` and apply via `make role`, before touching the next scaffold. Step 5 replaces the *entire* `terraform_pike` permission list with whatever candidates are being tested — it does not additively grant against a prior baseline — so starting the next type's test from anything but the placeholder risks a false "already works" result. The ideal reset would be an empty `permissions = []`, but the provider schema rejects that outright (`requires 1 item minimum` — confirmed, not assumed), hence the placeholder stand-in.

## Testing a `resource` instead of a `data` source

Resources are harder, for one structural reason: a **data source's `plan` makes a real API call** (a read), so `plan` alone is enough to discover its permission. A **brand-new resource's `plan` makes no API call at all** — it just proposes "will be created" locally. To discover `create`/`update`/`delete` permissions you must actually run `apply`/`destroy` against real infrastructure under `pike-service`. This changes the method:

1. **Use an isolated scratch Terraform config with local state — never the shared root module.** The root module's backend is the real GCS bucket (`terraform-pike-bucket-tfstate`) tracking everyone else's state; applying a new resource there would pollute it. Instead, create a throwaway directory (in the scratchpad) with its own `provider.tf` (project + `credentials = ".../pike-basic.json"`, no `backend` block → defaults to local `terraform.tfstate`) and the one resource block under test. `tofu init` there once; it's fully disposable.

2. **Pick a standalone candidate first.** Some resources need a real parent object to exist before they can be created at all (e.g. a Service Directory *service* needs a *namespace*; a Data Catalog *policy tag* needs a *taxonomy*). If a type has such a dependency, create the parent as `super` first (kept separate from the account under test, so its permissions are never conflated with the target's), then test the target's own CRUD permissions against that real parent. Prefer a standalone type when one is available — it avoids this entirely.

3. **Discover the full CRUD set, not just `create`.** Once `create` is confirmed necessary, it's reasonable to expect `get`, `update`, and `delete` are *also* needed for the full `apply` lifecycle (pike's own convention stores `apply` as the union of all four) — test for all four proactively rather than discovering each one serially:
   - `create`: `tofu apply` with nothing granted → read the 403, grant it, re-poll.
   - `get`: often surfaces immediately after — the provider does a post-create read-back to populate computed attributes, which needs its own permission distinct from `create`.
   - `delete`/`update`: exercise directly (destroy it; change an attribute and re-apply) rather than guessing — confirm each empirically, the same discipline as data sources.
   - Once all four are granted and the full lifecycle (create → modify → destroy) works, **minimality-check `plan` in isolation**: reduce to `get` alone and confirm a no-op `tofu plan` reports "No changes" cleanly — this is the type's true `plan` entry, separate from the `apply` superset.

4. **A resource's `create` can succeed even when the overall `apply` reports failure.** If the post-create read-back (`get`) is denied, Terraform errors out — but the `create` call itself already completed. **Never trust Terraform's reported success/failure alone for a resource** — after *any* apply attempt, verify real state directly (`gcloud <service> <type> list ... --account=super-...`). A "failed" apply may have left a real object behind that needs cleanup regardless of what Terraform's local state file shows.

5. **Never leave an orphaned real resource behind.** After every create/apply attempt in this flow, check real GCP state as `super` and clean up immediately — don't wait until the end of the session. If Terraform's own destroy path is blocked (e.g. `deletion_policy = "PREVENT"` refuses client-side, or state is inconsistent after a partial failure), delete the real object directly via `gcloud ... delete` as `super`, then `tofu state rm` to keep the scratch config's local state consistent. Confirm with a final `gcloud ... list` showing zero items before considering the type done.

6. **`attributes.<name>` entries are literal schema attribute names, not a fixed concept.** The mapping schema's `attributes` field (seen as `{"tags": []}` in `template.json`) holds extra permissions needed *only* when a specific **optional** attribute is set, beyond the base CRUD set — keyed by whatever that attribute is actually called in the resource's own schema (confirmed via `google_compute_instance`: `tags` there is the VM's network/firewall tags needing `compute.instances.setTags`, and `allow_stopping_for_update` needs `compute.instances.stop` — two unrelated attributes, each getting their own entry; `tags` in the template is just the common example key, not special). There's also a sibling `runtime` field for permissions the resource's *own* deployed identity needs (e.g. a Compute instance's service account reading a referenced secret) — a different concept from what `pike-service` itself needs to manage the resource; don't conflate the two.
   - **Don't assume an optional attribute needs nothing just because it sounds like local config.** Test it. `deletion_policy` on `google_service_directory_namespace` *looked* like a pure Terraform-local flag from its schema description alone — confirmed, not assumed, by actually setting each of its three values (`DELETE`/`ABANDON`/`PREVENT`) and observing real behavior: `ABANDON` let `destroy` "succeed" with zero `delete` permission granted (and left the real object behind — verified via `gcloud`, then cleaned up manually), and `PREVENT` refused with a pure client-side error even with full CRUD granted. Only after seeing both did it become correct to record no `attributes` entry for it.

7. **A resource that references another resource may need `get` on the *referenced* resource, not (only, or even at all) a permission on itself.** Found on `google_monitoring_snooze`: updating `display_name` on a snooze whose `criteria.policies` references an alert policy required `monitoring.alertPolicies.get` — permission on a completely different resource type. Worse: `monitoring.snoozes.update` (a real, GA, `gcloud iam list-testable-permissions`-confirmed permission for this exact resource) turned out to be **entirely unnecessary** — proven by removing it after the fact and watching the update still succeed. **A permission being real, correctly named, and listed as testable for a resource does not mean it's actually required for a given operation** — that list tells you what CAN be checked, not what IS checked for the call you're making. Minimality-check even "obviously correct" permissions discovered this way, the same as any guessed candidate.
   - When a generic 403 names nothing and naming convention doesn't obviously resolve it, `gcloud iam list-testable-permissions "//<service>.googleapis.com/<full-resource-path>"` returns GCP's own authoritative list of permissions checkable on that exact resource — a legitimate way to narrow candidates (seen here, and it's how `monitoring.alertPolicies.get` was found: by running the same command against the *referenced* resource, not just the one being modified, once the direct resource's own list didn't explain the denial).
   - An unusually long propagation wait (here: 15+ minutes, well past the ~2–6 minute range seen everywhere else) is itself a signal worth questioning once it's *that* far outside the normal range — it may mean the candidate is simply wrong/incomplete rather than still propagating. Don't let "maybe it just needs longer" become an excuse to avoid reconsidering the candidate.

8. **Some resource types have no delete API at all — a structural property of the type, not a permission gap.** `google_monitoring_snooze`'s own provider code emits an explicit warning: `"Monitoring Snooze resources cannot be deleted from Google Cloud. ... will be removed from Terraform state, but will still be present on Google Cloud."` Confirmed further: no `gcloud monitoring snoozes delete` command exists either. This means **any test object created for this type is permanently undeletable by anyone, including `super`** — a real exception to "never leave an orphan," not a failure to clean up harder. Flag this prominently to the user rather than silently accepting it; `destroy: []` is still the correct mapping entry (there's nothing to grant a permission *for*), but the real object persists (here: harmlessly, free, auto-expiring at its own `interval.end_time`).

9. **Clean up temporary dependency resources too, not just the primary resource under test.** When step 2's parent-dependency case applies (e.g. the alert policy a snooze's `criteria` needs to reference), that dependency was created as `super` specifically to make this test possible — it has no special protection and must be deleted once the target type's testing is done, the same as the primary resource. It's easy to clean up the thing you were directly testing and forget the scaffolding you built to test it.

10. **A deprecated resource may refuse all write operations at the product level, before IAM is even evaluated.** Seen with `google_data_catalog_entry_group`: `Error 400: Project {project} is not allowed to perform write operations due to {product} deprecation` — a clean `400`, not a `403`, that doesn't change no matter how long you poll or what's granted. This is a distinct outcome from every permission-denial case above: it means the *type itself* can no longer be live-verified on its write side via this harness, deprecated or not. Don't write a `verified_date` for a recheck that hits this — it never reached the permission-check stage, and stamping it would misrepresent "couldn't test it" as "confirmed accurate." Leave the existing mapping untouched and note the block. Check whether the deprecation warning names a replacement type (Terraform prints one, e.g. "Use `google_dataplex_entry_group` instead") — that's probably the type actually worth spending future effort on.

11. **Singleton/project-config resources can have `destroy` reuse `modify`'s exact permission, with no separate delete permission at all.** Found on `google_kms_project_autokey_config`: it isn't a creatable *object*, it's a project-scoped setting — confirmed because the very first "create" call's error named `cloudkms.autokeyConfigs.update`, not a `.create` permission (there isn't one). `TF_LOG=DEBUG` on an explicit `tofu destroy` confirmed this precisely: it issues the identical `PATCH .../autokeyConfig?updateMask=...` call as a real modify, just resetting the field to its default — there's no delete-style call to find a permission for. Recognize this pattern early: if the *create* error names an `.update` permission rather than `.create`, the type is very likely a singleton, and `destroy` should be tested expecting it to equal `modify`, not assumed to need its own distinct permission.
    - **When a candidate is confirmed correct (named explicitly, scope double-checked via `gcloud iam list-testable-permissions`) but stays denied far longer than anything else seen (here: ~24 minutes, a new high), don't assume the candidate must be wrong just because the wait is extreme.** First rule out a universal precondition by testing the identical call as `super` (if `super` also fails, it's not propagation — if `super` succeeds immediately, propagation delay for `pike-service` specifically is confirmed, and patience is warranted, however long it takes). Only reach for a different candidate once you have *some* positive evidence it might be wrong (e.g. a plausible alternative permission from `gcloud iam list-testable-permissions`), not just impatience — and even then, verify the alternative actually isn't also just propagation-delayed before concluding the first candidate was correct all along (it was, here: the "alternative" candidate added alongside a 20+-minute-delayed `get` turned out to be the unnecessary one once `get` finally landed, confirmed by a clean minimality re-check afterward).
    - This resource's `create` path left the real project in a genuinely changed state (`autokeyConfig` set to `ACTIVE`/`RESOURCE_PROJECT`) — not an "orphaned object" to delete, but an actual project-level configuration change. Verify it's been reset to its **exact original value** afterward (here: confirmed via the identical `etag` before and after), not just "destroyed" per Terraform's own report.

12. **Resource scaffolds are named differently from data sources.** `resource.ps1` creates `terraform/google/<resource>.tf` (no `data.`/`resource.` prefix) — not `resource.<name>.tf`. Confirm the exact filename a scaffold uses before assuming the data-source naming convention applies.

## Discipline

- **Never write a permission into a mapping file, or assert one is correct, without a live GCP response confirming it in that same session.** This was explicit, repeated user correction — guessing from naming convention or docs is exactly the failure mode this whole harness exists to prevent.
- **Never report an IAM change as applied because a `.tf` file was edited or `plan` was run.** Only `gcloud iam roles describe` (or equivalent live query) is evidence. `apply` is frequently auto-mode-blocked — check before assuming it ran.
- **Don't create real backing GCP objects to make a data source "succeed."** A `404 not found` on a placeholder ID is just as informative as a successful read for permission-discovery purposes, and far cheaper/safer. Only consider provisioning a real object if a type's API genuinely returns no distinguishing error without one — confirmed to actually happen (see the `biglake_hive_catalog_iam_policy` gotcha above) rather than assumed; when it does, report the type as blocked rather than writing a guessed permission.
- **Isolate before you plan.** A whole-directory `tofu plan` with multiple unfilled scaffolds produces undiagnosable noise; always narrow to one type per experiment.
- **For resources: never leave a real object behind, and never trust Terraform's own success/failure report as proof of what actually happened in GCP.** Verify with `gcloud ... list` as `super` after every apply attempt, clean up immediately if anything real was created, and don't assume an attribute needs no extra permission (or needs one) without actually setting it and observing real behavior — this applies as much to "looks like a pure local flag" attributes as to anything else.
